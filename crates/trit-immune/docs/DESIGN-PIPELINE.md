# 设计决策生产线：不审代码，审决策

> 病灶：如果每个 PR 都是设计问题，说明问题不在 PR 审查，而在设计决策
> **没有前置、没有沉淀、没有所有权**。PR 变成设计争论的现场，
> 等于用"逐单审代码"的方式承担整个系统的架构治理——必然累垮。

## 一、先分类：真设计问题 vs 伪设计问题

| 类 | 本质 | 处置 |
|----|------|------|
| 重复性设计争论 | 缺原则/缺契约/缺架构测试 | 解决一次，固化为规则，下次自动判 |
| 执行既有决策 | 设计早定了，PR 只是实现 | 快速通道，只查是否偏离契约 |
| 真正的新决策 | 触及公共接口/数据模型/安全边界/跨团队契约/不可逆迁移 | 唯一值得人类设计评审的一类——看决策本身，不逐行看 diff |

代码落点：`design::classify`——PR 模板强制栏（是否新决策？关联哪份 ADR？）
未填齐且触及设计边界的，**不进代码审查，退回设计队列**。PR 只承载已决策的实现。

## 二、按 可逆性 × 影响范围 分级

| 档 | 条件 | 处置 |
|----|------|------|
| `LocalReversible` | 局部可逆 | 默认原则 + 事后记录，不前置评审 |
| `LightReview` | 局部不可逆 / 跨模块 | 轻量设计说明，一个 owner 看，**限时默认通过** |
| `FormalRfc` | 跨团队 / 安全边界 / 不可逆迁移 | 正式 RFC，利益相关者评审 |

关键机制：**决策所有者 + SLA + 限时默认通过 + 异议升级**（`DesignQueue`：
`approve` 拍板权不可代理；SLA 到 0 → `DefaultApproved` 或 `Escalated`）。
否则设计评审变成新瓶颈。

## 三、案例法 → 成文法

每解决一次重复争论，问：这条结论能不能变成下次自动检查的规则？
能 → 沉淀为 `Statute`：架构原则 / 接口契约 / 架构测试 / 模式正反例。
`Statutes::arch_test` 在 DAG 上跑机器可查规则（如 `MaxFanIn`）。
**设计评审的量随规则积累下降，而不是随 PR 数量线性爆炸。**

## 四、AI 能做什么、不能做什么

- 能：检查 PR 是否偏离已记录 ADR/契约；分析依赖影响面（`propagate`/`coupling`）；
  生成 ADR 草稿与回滚提示；识别"这和之前某次争论是同一模式"（`vocab` 同构检测）；
- 不能替代：决策所有权（`approve` 拍板权不可代理）、跨团队利益权衡、
  不可逆迁移的最终拍板。
- 一句话：AI 把设计问题**分类、去重、补上下文**，把人类注意力压到真正新的决策上。

## 五、起步动作（已落地映射）

1. 定义设计敏感路径 → `DesignArea`；
2. PR 模板强制字段 → `PrIntake`（是否新决策 / 关联 ADR / 影响面 / 回滚方案）；
3. 未关联决策的敏感 PR → `classify` 退回设计队列；
4. 队列按可逆性×影响范围分级，owner + SLA + 默认通过 → `DesignQueue::tick`；
5. 每解决一次重复争论 → `Statutes::codify` 固化，`arch_test` 自动挡；
6. 海量普通 PR → 快速通道 + 抽样审计（逐单人审不 scale）。

一句话：如果每个 PR 都是设计问题，你缺的不是更强的审查，而是一层
**设计决策的生产线**。把设计从 PR 里剥出去，PR 才变回 PR；
把重复决策固化成规则，设计评审的量才会降下来。
