# trit-ops：三值推理算子库

三值的价值不在「2 bit 存得下」，而在**乘法可以完全消失**：权重只有 `{-1, 0, +1}`，
`x * t` 只可能是 `-x`、`0`、`+x`。本库把这一点落成两条真实可实现的主线：

1. **双导轨位平面**（每 trit 2 bit）：点积变成 4 组 `AND + popcount`；
   与 f32 激活相乘时变成按位掩码累加，**不做任何浮点乘法**。
2. **tryte 查表**（每字节 5 个 trit，`3^5 = 243`）：把 5 个 trit 的加权和预计算成
   一张 243 项的表，之后每个 tryte 只是一次查表。

> 三值在二进制硬件上始终是 2 bit（或 1.6 bit）模拟，没有「三值晶体管」。
> 本库只做能落地的东西。

## 算子清单

| 模块 | 内容 |
|---|---|
| `trit` | `Trit`（平衡 `{-1,0,+1}`）、乘/饱和加/Kleene `and`·`or`/Łukasiewicz、与 `trit_core::Ternary` 互转 |
| `pack` | `Rail` 双导轨（2 bit/trit，`AND+popcount` 点积）、`Trytes`（5 trits/byte，base-3 编码） |
| `quant` | `absmean` / `absmax` / 三电平 Lloyd-Max `1.224σ`，含 rel_err 与零占比报告 |
| `gemv` | `TernaryMatrix`（标量/掩码内核）、`TryteMatrix`（`3^5` 查表内核）、`Kernel::Auto`（双导轨矩阵上没有 tryte 视图，等价于掩码） |
| `simd` | AVX2/FMA 内核；同时提供 f32 / f16 / Q4_0 基线，保证同一份代码、同一个线程池 |
| `pool` | epoch 自旋线程池，单次派发约 1 µs |

## 实测一：流式（内存墙）

1.34 亿参数一次性过一遍，工作集远大于缓存，测的是**内存墙**。
本机 24 核（Intel Ultra 7 270K Plus），8 线程，`bench --stream`：

| 内核 | GMAC/s | 有效带宽 | 相对 f32 | max_err |
|---|---|---|---|---|
| f32（4 B/参数） | 8.20 | 32.81 GB/s | 1.00× | 3.1e-5 |
| f16（2 B） | 17.14 | 34.27 GB/s | 2.09× | 3.1e-5 |
| Q4_0（0.5 B） | 61.13 | 30.56 GB/s | 7.45× | **1.2e-1** |
| trit 双导轨掩码（0.25 B） | 86.00 | 21.50 GB/s | **10.49×** | 2.9e-5 |
| trit tryte 查表（0.2 B） | 124.43 | 24.89 GB/s | **15.17×** | 3.1e-5 |
| trit 自动选核 | **129.83** | 32.46 GB/s | **15.83×** | 3.1e-5 |

同机重复测量波动约 ±5%（f32 8.20–8.32、tryte 122–124 GMAC/s）。

**2026-10-26：掩码内核改为 4 路累加器。** 原来单个 `acc` 把每 64 trit 的 16 次 add/sub
串成一条 AVX 加法依赖链（延迟约 4 周期 → 下限约 64 周期/64 trit），把内核锁在 ALU 上；
拆成 4 路后每路链长 4，瓶颈回到访存。交替 5 轮配对（1acc vs 4acc 背靠背，同进程）：

| 轮 | 1acc GMAC/s | 4acc GMAC/s | 变化 |
|---|---:|---:|---:|
| 1 | 97.15 | 133.10 | +37.0% |
| 2 | 110.35 | 120.33 | +9.0% |
| 3 | 78.40 | 105.24 | +34.2% |
| 4 | 92.32 | 100.64 | +9.0% |
| 5 | 59.65 | 79.05 | +32.5% |

**5/5 配对为正，配对比值中位 +32.5%**（符号检验 p = 1/32 ≈ 0.03）；`max_err` 不变（3.1e-5）。
这与下面「掩码内核还有约 30% 空间、瓶颈是指令密度」的判断吻合。

⚠️ **上表的绝对值是机器空闲时测的；本轮测量期间绝对值波动到 59.65–110.35 GMAC/s（±30%），
是持续负载下的降频。所以只有「相邻两轮配对」可信，不要拿本轮绝对值与上表直接比。**

**2026-10-26：掩码内核改为行阻塞 2**（两行共享一次 `x` 装载）。每 8 trit 的装入从
3 次降到 2.5 次（省一次 32 B x 装载），两行各 4 路累加器，输出与单行版**逐位一致**
（`mask_pair_matches_single_bitwise` 覆盖奇数行的成对+尾行两条路径）。
`bench --mask-pair` 交替 21 轮（同进程、背靠背）：

| 形状 | 单行 ns | 两行 ns | 两行/单行 | 两行更快 |
|---|---:|---:|---:|---:|
| 1536×576 | 10975.9 | 10807.0 | 0.985 | 15/21 |
| 8192×576 | 45364.0 | 43379.6 | **0.956** | 14/21 |
| 49152×576 | 280341.5 | 251212.5 | **0.896** | **16/21** |

收益随行数增长（大行数时 x 的重复装载更值钱），小行数无可测变化。
绝对 GB/s 表没有重测——本轮机器有并发负载，按上面的纪律只报配对值。

读法：

- f32 / f16 / Q4_0 都跑在 **33 GB/s**，这是本机这条访问路径的墙。
- 三值的倍数**全部来自少读字节**：0.25 B 与 0.2 B 对 4 B。
- 掩码/查表内核只跑到 21.5–24.9 GB/s，没打满 33 GB/s 的墙；自动选核能到 32.5 GB/s。
  说明掩码/查表还有约 30% 空间
  （瓶颈是每 32 个 trit 一次查表/掩码的指令密度，不是内存）。
- **精度上三值反而更好**：Q4_0 的 1.2e-1 来自激活被量化成 Q8；三值权重本身精确，
  误差只有 f32 舍入的 3e-5。

## 实测二：分形状（内核效率）

SmolLM2-135M 的 decode 真实形状，按每 token 出现次数加权折算。
**注意：这些矩阵都小于缓存，这一节测的是内核效率，不是内存墙。**

| 内核 | ms/token | 折算 tok/s | 相对 f32 |
|---|---|---|---|
| f32 | 3.95 | 253.4 | 1.00× |
| f16 | 2.33 | 429.3 | 1.69× |
| Q4_0 | 2.33 | 428.5 | 1.69× |
| trit 双导轨掩码 | 1.92 | 520.8 | 2.06× |
| trit tryte 查表 | 3.70 | 270.0 | 1.07× |
| **trit 自动选核** | **1.67** | **597.5** | **2.36×** |

（3 轮中位数，每轮内 7 个内核相邻测量；逐轮原始值用 `bench --rounds 3` 可复现。）

三个结论，包括一个已经修掉的负结果：

- **查表内核的小行数亏损已修。** 原来每次 gemv 都要重建 `gpr × 243` 项的表，
  576 行的 matvec 里建表成本盖过查表收益，掉到 **0.40×**。现在按行数自适应表粒度
  （见下面「建表 vs 查表」），同一张表只剩 **1.07×**——快 **2.56×**，从「比 f32 慢 2.5 倍」
  变成「比 f32 快」。
- **查表仍然打不过掩码**（1.07× vs 2.06×），所以小行数该走掩码。自适应解决的是「不再灾难」，
  不是「变成最优」——这个区别要写清楚。
- **基准里的「自动选核」按行数选核**：只有行数 ≥ 40960 才走查表，其余走掩码。
  注意这是 `bench` 自己的策略；库里的 `Kernel::Auto` 作用在 `TernaryMatrix` 上只能走掩码
  （双导轨矩阵没有 tryte 视图），要查表得显式用 `TryteMatrix`。

  这个阈值是实测重定的（`--pair 掩码 tryte --rounds 7`，cols=576）：

  | rows | tryte/mask | tryte 更快 |
  |---:|---:|---:|
  | 1024 | 0.477 | 0/7 |
  | 2048 | 0.613 | 1/7 |
  | 4096 | 0.373 | 0/7 |
  | 8192 | 0.955 | 3/7 |
  | 16384 | 0.822 | 0/7 |
  | 32768 | 0.966 | 2/7 |
  | 49152 | **1.085** | **7/7** |

  **查表只在 49152 行可靠取胜（+8.5%，7/7）**，其余全部落后。原先写的 2048 是错的，
  会让 2k–40k 行都走更慢的查表。4096 那行 0.373 明显是离群值（邻居都在 0.8–0.97），
  但即使按邻居算，结论不变。
- ⚠️ **表内行不要横向比当精确排名。** 各内核虽然已经轮转测量，机器本身的漂移仍能到 ±40%
  （看上面 tryte 是 ±4%，掩码是 ±43%）。判 A 比 B 快用 `bench --pair A B`，它给逐轮配对和符号检验。

## 建表 vs 查表（`bench --split`）

tryte 的成本 = **建表**（`O(gpr × 3^g)`，与行数无关）+ **查表**（`O(rows × gpr)`，与行数成正比）。
小行数时建表是固定大头，所以把每个 5-trit 字节拆成「低 2 位 + 高 3 位」两张小表：

| 表粒度 | 每字节项数 | 建表 | 查表 |
|---|---:|---|---|
| 整字节 `g=5` | 243 | 贵 | 每字节 1 次 |
| **拆表 `2+3`** | **36** | **便宜 6.75×** | 每字节 2 次 |

拆表的两次查表需要 `code % 9` / `code / 9` 定位；这两条整数运算换成 243 项 `u16`
映射表（486 B，常驻 L1）后，**查表快 13.6–19.1%**（`bench --split-map`，4 个行数档 × 7 轮，
每档 7/7 胜，中位比 0.864 / 0.809 / 0.824 / 0.830；两种写法结果逐位一致，有单测锁住）。
注意这只优化了查表本身，**交叉点没动**：

| rows | 拆表 / 整表（旧：`%9`/`/9`） | 拆表+映射 / 整表 |
|---:|---:|---:|
| 576 | **0.205×** | **0.245×** |
| 1536 | **0.378×** | **0.328×** |
| 1792 | — | **0.349×** |
| 2048 | 1.161× | 1.067×（±0.1） |
| 4096 | 1.112× | 1.228× |

阈值仍取 `LUT_SPLIT_ROWS = 2048`：低于它走拆表（现用映射查表），高于它走整表。
`gemv_with_split_tables`（`%9`/`/9`）保留为 A/B 基线，`gemv_auto` 走 `gemv_with_split_tables_map`。

⚠️ **建表必须用差分法测**（`全量 gemv − 只查表 gemv`）。直接给建表循环计时会被编译器优化掉
——表写进去没人读，死存储消除，测出来只有真实值的一半以下。第一版就是这么错了一次。


## 接进引擎：端到端 tok/s（2026-10-25）

已接入一个本地推理引擎（不在本仓）：`--ternary` 逐行 scale 时额外建一份
`TernaryMatrix`，matvec 改走 `row_dot`，用引擎自己的自旋池按行驱动。

SmolLM2-135M，8 线程，decode tok/s，同机：

| 配置 | tok/s | 输出 |
|---|---|---|
| f16 | 101.7 | 连贯 |
| Q4_0 | 176.9 | 连贯 |
| 三值 · 旧标量分组 | 12.13 | 退化 |
| **三值 · 双导轨掩码** | **320.31** | 退化 |
| 三值 · 双导轨 + Lloyd-Max scale | 365.39 | 退化 |

换内核本身 **26.4×**（12.13 → 320.31），相对 Q4_0 1.81×、相对 f16 3.15×。

**但输出是坏的**：三值配置全部退化成重复 token。对照实验 `--ternary --deq`
把同一批三值权重反量化回 f32 再走原 f32 路径，输出**同样退化** ⇒ 数值链路没写错，
掉点来自 post-training 量化本身，与 stories15M 上的结论一致。

所以 320/365 tok/s 只是算子级结论，**不是可用推理配置**。

**后续（2026-10-25）：QAT 权重已经做出来了，输出连贯。** 对 stories15M 做 BitNet 式
STE 微调（2500 步、573 秒、CPU），三值化规则与引擎一致，结果：

| 配置 | 输出 | tok/s |
|---|---|---|
| QAT 权重 + 三值 | **连贯**（`there was a little girl named Lily…`） | 1974–2294 |
| 原始权重 + 三值 | `time time time …` | 1953–2238 |
| QAT 权重不量化（f32） | 退化（重复句） | 215 |

潜权重不量化反而更差——这正是 QAT 在优化「量化后」的形式。

## 正确性

- 25 条测试全绿：打包/解包在 0/1/4/5/6/63/64/65/100/127/128/200/576 等长度上往返；
  三条内核（标量 / 掩码 / 查表）与标量参考逐元素对齐；`cols` 不是 5 的倍数时也覆盖。
- 基准里每个内核先跑一次与标量参考比对，`max_err` 列即证据。
- `Rail::from_planes` 拒绝正负导轨重叠与尾部脏位；`Trytes::from_codes` 拒绝 ≥243 的码。

## 边界（不要过度解读）

- **流式基准是单一大矩阵**，真实模型是 210 个不同形状；分形状那一节才是形状分布，
  但它驻留缓存。两者互补，任何单独一个都不是端到端。
- **本库不声明模型质量**。三值权重在基准里是随机生成的；三值能否不掉点取决于
  权重来源（QAT），那是模型侧的事，算子库不负责。
- 端到端 tok/s 需要把内核接进推理引擎才能给；本文只给算子级倍数。

## 工具（`bench`）

长跑不沉默：每轮结束立即 flush 一行，不用等到底。

| 用法 | 作用 |
|---|---|
| `bench` | SmolLM2 形状集 |
| `bench --stream --iters 3` | 流式（内存墙） |
| `bench --rows 576 --cols 576` | 单形状 |
| `bench --rows 576 --cols 576 --rounds 5` | **轮转测量**：每轮把所有内核各测一遍，取中位数并报各轮波动 |
| `bench --rows 576 --cols 576 --rounds 5 --pair 掩码 tryte` | **配对比较**：两个内核的逐轮值与符号检验 |
| `bench --rows 576 --cols 576 --split` | **成本分解**：tryte 建表 vs 查表，两种表粒度 |

为什么需要轮转：顺序测量时先测的内核和后测的拿到的机器状态不同，实测同一段代码换个位置
读数能差约 25%。轮转让每个内核都经历全部位置，中位数把位置偏差摊平。
跨版本 A/B（同一个内核、两次编译）仍需要两个二进制交替跑——那是唯一能隔离代码差异的办法。
