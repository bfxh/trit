# t3 — 三值逻辑二进制分诊引擎

面向逆向工程的三值（Kleene K3 / Belnap FOUR）分诊工具链。零第三方依赖，`t3-core` 禁止 `unsafe`，SIMD 内核带标量参考实现。

**一句话**：把「不知道」当成一个必须被计算、被传播、被报告的值，而不是一个悄悄退化成 `false` 的分支。

```bash
cargo build --release
./target/release/t3 selftest                                  # 运行时自检
./target/release/t3 scan   C:/Windows/System32 --quiet        # 批量分诊
./target/release/t3 explain C:/Windows/System32/notepad.exe   # 单文件证据与反事实
./target/release/t3 bench  --dir C:/Windows/System32          # 实测吞吐与阈值标定
```

退出码本身编码了三值：`0` 确定干净 · `1` 可疑 · `2` 确定恶意 · `3` 未定 · `4` 证据冲突 · `10` 用法/IO 错误。

---

## 1. 为什么要三值，而不是分数

传统分诊给每个特征加权求和，再和一个魔数阈值比较。这个模型有三个致命问题：

| 问题 | 后果 |
|---|---|
| 「没测到」和「测到了，是干净的」混为一谈 | 截断文件、损坏节表、读不全的导入表全部报成 clean |
| 单点估计掩盖测量噪声 | 熵 7.19 与 7.21 落在阈值两侧，判定从「干净」跳到「加壳」 |
| 分数可被叠加放大 | 同一个检测器触发两次就能制造严重度；没有证据守恒 |

`t3` 用三个机制分别对应：

1. **事实默认 `Unknown`**。解析器读不到就不写 `false`，`Unknown` 一路传播到判定。
2. **判定带代替阈值**。连续测量落进标定出的模糊区间时报 `Unknown`，并附带实测数值。
3. **等级用格的最大值合并，而不是求和**。`Clean < Suspicious < Malicious` 的最大值是**格并**——幂等、可交换、可结合，因此证据重复不会放大严重度（求和会）。

## 2. 三个可验证的设计主张

### 2.1 假设代数禁止否定，因此区间语义是精确的

`Expr` 没有 `Not` 构造子，只能由 `∧`、`∨` 和正事实引用组成，因此对每个事实单调。这带来一个**可证明**的性质：

```
lo = 把所有 Unknown 事实强制为 False 后求值
hi = 把所有 Unknown 事实强制为 True  后求值
```

对单调公式，这两个值是所有 `2^k` 种「未知补全」下的**最小值和最大值**，所以 `[lo, hi]` 是紧的、可靠的包围。一次遍历同时算出两端，成本等于一次普通求值。

> 这一条不是声明，是测试：`expr::tests::interval_equals_exhaustive_enumeration` 对 4 个公式穷举全部补全，逐一比对区间端点。`t3 selftest` 在运行时再验一遍。

否定没有被消灭，而是**下沉到叶子**：检测器直接判定 `signed.present`，假设只正向消费它。这也是为什么规则语言支持 `forbid`（它在假设层之前就被归约成单个 trit）。

### 2.2 Belnap FOUR 用于「冲突」，但它是双格不是 De Morgan 格

签名过的程序同时结构像加壳——这不是「真」「假」或「不知道」，而是**两边都有证据**。`B4` 用两个独立比特 `(支持真, 支持假)` 表示，合并是逐位或。

开发中被测试抓到一个错误：最初我按「分配格 + De Morgan」写断言，`¬(T ∧ F) = N` 却不等于 `¬T ∨ ¬F = B`。查明后确认 FOUR 是**双格（bilattice）**：逐位与/或是**信息序**上的格运算，取反交换双轨、保持信息序、反转真值序。De Morgan 在此格上不成立，代码与文档都不再依赖它。

实际需要的是更弱、也已满足的性质：合并可交换、可结合、幂等，且只增不减——这正是判定与检测器顺序、线程调度无关的原因。

### 2.3 字节缺失必须传播为 `Unknown`，不能是「没命中」

签名引擎的每个位置有四种谓词：必须等于、任意、**必须不等于**、属于集合。`Region` 同时携带 `data` 和 `declared_len`，所以一个节区「声明 0x2000 字节、文件只有 0x800」是可以被识别的。

于是「存在某处匹配」按 Kleene 析取求值：

- 某个完整窗口命中 → `True`
- 所有可测位置都测过且不命中 → `False`
- 没有命中，但有关键位置落在文件没有的字节里 → **`Unknown`**

布尔匹配器把第三种报成「没命中」，这与真的阴性无法区分——这正是下载被截断、或节表被改掉一个节区的样本能拿到「干净」结论的原因。

同时区分**适用性**与**可判定性**：规则作用域是 `.rsrc` 而文件没有 `.rsrc` 时，这是可判定的「不适用」（结构被成功读取并如实声明了），不是 `Unknown`。若混为一谈，每条规则都会给每个文件贡献不确定性，判定永远未定——理论上精确，工程上废掉。`Hit` 同时携带 `value` 与 `applicable`，报告可以分开陈述。

## 3. 实测结果

全部在本机测（Windows 11，x86_64，32 逻辑核，AVX2），语料为 `C:\Windows\System32` 全量。

### 3.1 误报：干净语料上的恶意判定为 0

```
扫描 25424 个文件 · 12.34 GiB · 6.76 s · 1.83 GiB/s · 3761 文件/s

确定干净 19481 (76.6%) · 可疑 1399 (5.5%) · 恶意 0 (0.00%)
未定  4213 (16.6%) · 冲突 7 · 跳过 342（权限拒绝）
```

25 424 个已知干净的系统二进制上，`malicious` 判定数 **0**。这不是调参调出来的：过程中暴露并修掉了四个真实误报源，每一个都由数据而非猜测定位。

### 3.2 标定：阈值来自分位数，不是拍脑袋

`section.high_entropy` 的判定带由 6 503 个可执行节区的测量分布确定：

```
p50 6.115 · p95 6.487 · p99 6.643 · p99.5 6.675 · p99.9 7.369 · max 7.930
```

`lo = p99.5`、`hi = p99.9`：0.5% 的干净文件落进未定带，0.1% 高于它。这两个数字就是规则的真实代价，不是什么「高精度」的说法。

### 3.3 内核

| 内核 | 标量基线 | 优化版 | 倍数 |
|---|---|---|---|
| 字节查找（128 MiB，全扫描） | 1.87 GiB/s | **26.98 GiB/s** (AVX2) | 14.4× |
| 字节计数（32 MiB × 4 针） | 0.71 GiB/s | **5.12 GiB/s** | 7.2× |
| 熵直方图（32 MiB，75% 零字节） | 1.0–1.3 GiB/s | **1.8–2.1 GiB/s** (4 交错表) | 1.5–1.8× |
| 熵直方图（同上，均匀随机） | 1.7–2.0 GiB/s | 1.7–2.1 GiB/s | ≈1.0× |
| 纯内存分析（解析+特征+签名，单线程） | — | 0.50 GiB/s | — |

三个值得记住的结论：

- **熵的加速取决于数据偏斜，不取决于技巧。** 均匀数据上单表几乎不停顿，交错表只赚个位数百分比；真实二进制（填充、对齐、重复机器码）能赚 1.5–1.8×。
- **最需要熵的文件收益最小。** 加壳/加密节区本身就是均匀数据。任何单一「熵快 N 倍」的数字都是双峰分布的一半。
- **8 张表与 4 张表在噪声内无法区分**，所以默认用 4 张：一半 L1 占用，没有可测损失。8 表版本留在树里，是为了能在别的硬件上重做这个对比，而不是让人凭信。

### 3.4 两次基准代码的自我打假

- 第一版基准用 `let _ = f()` 丢弃返回值，优化器把整个循环当死代码消掉，报出 **104 166 GiB/s** 的字节计数。加上 `black_box` 后回到真实量级。
- 第二版 `black_box` 搬运 1 KiB 直方图返回值，代价超过被测差异本身。改成在闭包内归约为校验和后噪声才可接受。

基准测错的方向永远是「偏快」，所以这类错误必须由自己抓出来。

## 4. 结构

```
crates/
  t3-core/     决策层，无 I/O、无 unsafe
    tri.rs       K3 强 Kleene（∧=min，∨=max，U 是 ¬ 的不动点）
    b4.rs        Belnap FOUR，双比特，合并=逐位或；文档记录 De Morgan 不成立
    band.rs      判定带与分位数标定
    fact.rs      45 个固定事实槽，零分配的 [Cell; 45]
    expr.rs      单调假设代数，区间语义精确
    verdict.rs   等级格并、Belnap 冲突、反事实分析
    rules.rs     20 条内置假设
  t3-kernel/   热循环
    scan.rs      AVX2/SSE2 find/count/nonzero + 标量参考
    entropy.rs   4/8/1 交错直方图，全部带标量基线
  t3-format/   零拷贝、无 panic 的容器分诊
    reader.rs    全边界检查读取器（无 unsafe）
    pe.rs        PE32/PE32+：节区、叠加段、PDB、Rich、TLS
    pe/imports.rs  导入表解析与能力位分类
    elf.rs       ELF32/64、双字节序、动态符号、build-id、GNU_STACK
    detect.rs    解析结果 → 三值事实；标定带集中在此
    detect/elf_fill.rs  ELF 侧的事实填充
    region.rs    带截断标记的具名区域
  t3-sig/      三值签名
    pattern.rs   四态逐字节谓词 + 存在性位图预筛
    rule.rs      规则语言、 applicability、三值求值
    builtin.rs   12 条内置规则（纯文本，走同一套解析器）
  t3-cli/      scan / explain / sig / bench / selftest
```

t3 与主仓共用一套门：`scripts/module_budget.py` 会扫 `t3/crates`（单文件 800 行上限），
`.github/workflows/t3.yml` 跑 fmt / clippy `-D warnings` / test。

**测试**：102 个单元测试 + 1 个文档测试，全部通过。包括格律穷举、区间语义穷举、SIMD 与标量在每一种对齐与长度下的等价、截断区域传播、随机缓冲区不 panic、规则解析错误定位。

## 5. 开发中被数据改掉的四个判定

这四条都是先写错、再被真实语料推翻的。留下来是因为它们是这个工具真正的价值来源。

1. **`imports.absent` 在 39% 的干净文件上为真**（`KernelBase.dll` 曾报注入三件套）。前者是 `.mui` 资源 DLL 本来就没有导入表；后者是我把 `NtAllocateVirtualMemory` 这类**通用内存 API** 算进了「远程注入三件套」。真正的注入三步是 MITRE T1055 的 `VirtualAllocEx` + `WriteProcessMemory` + 远程线程原语。
2. **`ntoskrnl.exe` 被判可疑**，因为 `Pad2`/`Pad3` 是链接器生成的填充节区：有虚拟大小、无原始数据、可执行——和加壳器的空壳节区完全同形。
3. **时间戳「早于 1980」判据全量误报**。现代 MSVC 的 `/Brepro` 把 `TimeDateStamp` 写成确定性哈希，系统二进制里满是 1970 年和未来的值。只剩「等于 0」还有意义。
4. **所有显卡驱动被判加壳**。`amdocl64.dll` 的高熵在 `.data`（编译好的 GPU 内核），不在代码段。`section.high_entropy` 因此拆成「可执行节区高熵」与「非可执行节区高熵」两个事实。

第 4 条还带来一个严重度模型的修正：**能力 ≠ 恶意**。调试器、浏览器沙箱代理、Windows 自己都链接注入原语，这是个设计事实。所以现在 `Malicious` 要求「能力 **且** 结构隐蔽」，单纯具备能力只到 `Suspicious`。

## 6. 边界与已知问题

- **不做反汇编，不做行为判定。** 这里全部是元数据：节区、导入名、熵、时间戳。因此它只能说「攻击面」和「结构反常」，不能说「这段代码在做什么」。
- **没有时态逻辑、没有 SMT、没有完整硬件仿真。**
- **签名引擎是单线程瓶颈**（0.50 GiB/s）。当前用单字节存在性位图预筛，对大文件筛选力有限；下一步应是 16 位锚点位图或真正的多模式自动机，预计 5–10×。
- **叠加段熵阈值未标定**：干净语料里只有 4 个文件有叠加段，样本不足以定分位数。这是唯一一个「先验而非实测」的阈值，代码里已如实标注。
- **`file.high_entropy` 不参与 PE/ELF 的假设**：节区熵严格优于它。它只对未识别容器的输入有意义。
- **Authenticode 只检查目录是否存在，不验证签名。** 「已签名」在这里是**解释**（解释不了的加壳才叫冲突），不是「可信」。
- 语料偏差：全部标定来自 Windows 系统二进制。对企业软件、游戏加壳、恶意样本的分布没有测量，阈值迁移到那些域需要重新标定。

## 7. 与参考项目的关系

设计时读过 [`bfxh/trit`](https://github.com/bfxh/trit)（克隆在 `../ref/trit`，仅阅读未编译）。它把「未知」作为一等公民这一点是对的，`trit-re` 的 `Judgment`（支持/反驳/未决三栏）与 `benign` 解释产生四值冲突的思路值得借鉴。

刻意不同的三处：

1. **它的事实 id 是 `&'static str` + `BTreeMap`，每次查找分配 `String`**；这里是 45 个固定槽位的栈数组，每文件零分配。
2. **它的假设表达式含 `Not`/`Xor`/`Implies`/`Equiv`**，因此无法做可靠的区间语义，只能给单点结论；这里禁止否定以获得**精确且可穷举验证**的包围。
3. **它没有三值签名引擎。** 这里是 `required / forbidden / indifferent` 三态逐字节 + 截断传播，这是整个工具链里最独特的部分。

它自己的 `docs/TERNARY-BOUNDARIES.md` 定了硬规矩：*任何对比都必须同时给二进制基线，没有基线不算结论*。本项目的所有性能数字都遵守这条。
