# 分层与归位规范（算子 / 算法 / 学习 / 生产链）

> 一句话：**本仓是底座，不是工具箱**。算子、算法、学习机制在这里实现一次；
> 生产链（把底座接到某个产品/数据/服务上的那层代码）在其他仓。
> 「改名」不在本规范里——仓名就是 `bfxh/trit`，要改也是最后一步单独动作。
>
> 本文件是**判据**，不是愿望。每条规则后面标了它靠什么落地：`表` = `scripts/layers.json` 登记，
> `门` = CI 里能判红的脚本，`人` = 只能靠评审（这类要尽量少）。

## 1. 四层定义

| 层 | 名字 | 判据（满足全部） | 本仓落位 |
|---|---|---|---|
| **L0** | 语义与表示 | 只定义值域/代数/编码，不做「问题求解」；换掉上层任何一个它都不动 | `trit-core`（algebra / ast / parser / value / limits） |
| **L1** | **算子库** | 输入→输出的**单点计算件**：给一批 trit 回来一批值；有明确的每秒吞吐口径；能被别家内核逐元素替换 | `trit-ops` `trit-dot` `trit-float` `trit-gpu` `trit-attn` `trit-codec` `trit-texture` |
| **L2** | **算法库** | 解一个**问题**（等价性、可满足、计数、量化、化简、调度、验证）；有 oracle 可对拍；正确性优先于速度 | `trit-eval` `trit-sat` `trit-bdd` `trit-count` `trit-circuit` `trit-policy` `trit-schedule` `trit-graph` |
| **L3** | **学习库** | 会**改参数**：训练循环、量化/STE、评测、清单与复核；产出是权重 + 可复现记录 | `trit-learn` `trit-train` `trit-parts`（含 `parts-depth*`） |
| **L4** | 生产链与外壳 | 把 L0–L3 接到某个具体产品/平台/流程：CLI、语言服务器、CI 机器人、逆向靶子、安全面、伞包 | `trit-cli` `trit-lsp` `trit-build` `trit-vcs` `trit-orch` `trit-wasm` `sansheng` `trit-re` `trit-immune` `trit-net` `trit-redteam` `trit-procscan` `trit-unsafe` `trit-capacity` `trit-machines` |

**「不可能只有这四类」是对的**——这四类是**归位判据**，不是目录数。落不进任一层的代码就是**不该进本仓**（见 §4）。

## 2. 依赖方向（可判红）

- 只允许 **上层依赖下层**：L4 → L3 → L2 → L1 → L0，同层之间允许但必须点名原因。
- **禁止**：L1 依赖 L2/L3（算子为了跑自己的基准去链求解器）、L2 依赖 L3、任何跨层回边。
- `trit-count` → `trit-bdd` 这类**同层**依赖要登记原因（一个引擎给另一个当第三方对拍）。
- 落地：`门` `scripts/layer_gate.py` 读 `scripts/layers.json` + 各 `Cargo.toml` 的内部依赖边，出现回边判红。

## 3. 新东西进来时放哪（这是你日常最痛的一步）

按顺序问，第一个「是」就是它的层：

1. 它只是**换一种值域/编码**（三值→四值、双导轨→位平面）？→ **L0**。
2. 它的正确性说法是「**同样输入更快/更省**」，且能对拍逐位一致？→ **L1**。
3. 它的正确性说法是「**这个结论对不对**」（等价/可满足/计数/量化/验证），需要 oracle？→ **L2**。
4. 它会**改参数**，产出权重或指标，需要清单+复核？→ **L3**。
5. 它回答的是「**接到某个产品/平台上怎么用**」？→ 那是生产链，**不进本仓**（放对应项目仓，按 git pin 依赖这里）。

**移植外部算法**（把某个现成算法用三值/四值重写）走同一条路：移植品进它**语义所在的那一层**，
并在该 crate 的模块头写清 `移植自 <项目/论文 @ 版本>` 与**差异**（值域、语义、精度）。
不因为「它是某个项目的算法」而留在项目仓——那正是现在来回搬代码的根源。

## 4. 去重与筛选（你说「筛选太差 / 算法完全一样」）

三条硬规则，全部要能判红：

- **一个能力一个权威实现**。第二个实现必须在 `scripts/layers.json` 里写 `alternative_of: <crate>`，
  并带**同机同输入的实测差**（>10% 才允许并存，否则删一个）。没有读数 = 判红。
- **oracle 与被测不能同体**。L2/L3 的每个新实现必须指出它对拍谁（穷举 / 闭式解 / 另一引擎 / 上游参考实现）；
  只跟自己比的不算筛过。
- **规模口径要写**。性能声明必须带规模档（n=？、K=？、带宽还是指令数），
  跨构建对比必须交错测（热漂移 ±25% 会把 32% 读成 13%）。

## 5. 外部项目怎么拿（已定：git pin + tag）

- 生产链仓写 `trit-ops = { git = "https://github.com/bfxh/trit", tag = "v0.12.x" }`，
  **不复制源码、不 vendor**。
- 底座侧承诺：**L0/L1/L2 的 public API 只在 tag 边界变**；要动签名，先发 `deprecated` 一个 tag，
  下个 tag 才删。生产链适配代码因此可以只留一处薄的 pin 层，而不是每个项目抄一份胶水。
- 发布面规则不变：可发布 crate 不得依赖 `publish = false` 的 crate（`publish_graph.py` 已在判红）。

## 6. 改名是另一个动作

仓名保持 `bfxh/trit`。真要改名，顺序固定：
① 本规范的门先进 CI 并绿；② 外部 git pin 全部改成 tag 依赖且能独立构建；
③ 一次改完 remote + 文档引用 + `_handoff` 三件套；④ 旧名留重定向并实测 cargo 是否吃重定向——
**实测不过就别改**，把证据写进 CHANGES。
