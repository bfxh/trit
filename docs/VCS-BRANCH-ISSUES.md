# trit-vcs 分支与更新问题清单（主库侧观察）

## 0. 口径

每条都标来源：

- `账本`：`_handoff/LEDGER.md` / `CHANGES.md` 的既有记录；
- `实测`：在主库的多 worktree 上可直接复现；
- `待查`：没有读到实现细节，不写成结论。

本文件不是 `trit-vcs` 的完整审计，只是把主库侧撞到的问题集中到一处，避免每个会话重新踩。

## 1. 已确认的问题

### 1.1 `pull` 不动客户端 HEAD，也不删多余文件（账本 A344）

- 现象：`trit-vcs pull --central <path>` 只做树清单 + 稀疏物化；客户端 HEAD/ref 不变，工作区多余文件保留。
- 影响：拉取后“当前分支”与实际文件不一致；`pull` 不能完成“更新分支”。
- 建议：`pull` 增加 `--update-ref <branch>`：快进才写 ref，分叉拒绝；报告未跟踪/多余文件。

### 1.2 中央仓是另一个目录（账本 A344）

- 现象：无网络协议、无鉴权、无跨机认领表；多人并发更新同一 ref 没有仲裁。
- 影响：并发更新可能互相覆盖；冲突只能事后人工发现。
- 建议：ref 写入用 compare-and-swap（旧值不匹配即拒绝），失败原因结构化。

### 1.3 squash 合并后的本地分支判定（实测）

- 现象：PR 以 squash 合并后，`git branch -d <feat>` 报“未合并”，因为历史没有 ancestry；内容其实已在 main。
- 影响：分支清理不能只看 `git branch --merged`；会留下大量“看似未合并”的分支。
- 建议：以 PR 状态（MERGED）+ 远端分支已删为准；`-D` 前先核对 PR head SHA。

### 1.4 一个分支只能在一个 worktree 检出（实测）

- 现象：多会话并行时，`git switch` 同一分支失败；`git worktree add` 同分支也被拒。
- 影响：并行会话必须各自开分支；分支命名冲突/残留会阻塞新会话。
- 建议：会话启动脚本生成唯一分支名（`feat/<主题>-<会话id>`）；收工按 PR 状态回收 worktree。

### 1.5 同一 worktree 内并行切分支会导致起点漂移（实测）

- 现象：主库某个 worktree 的 HEAD 从自建分支被更新到别人的合并提交；`git log main..HEAD` 一度为空。
- 影响：提交可能落到错误基线；PR diff 混入别人的提交。
- 建议：一个 worktree 固定一个分支；切分支前 `git status` 必须干净，且由同一会话独占。

### 1.6 发布/合并分支的命名与清理没有统一入口（实测）

- 现象：`feat/*`、`fix/*`、`docs/*` 混用；临时 worktree 与本地分支在合并后残留。
- 影响：`git branch` 列表噪声大；新会话难以判断哪些分支还活着。
- 建议：主库脚本统一“创建 → 推送 → 合并 → 回收”的命名与状态机；文档只列规则，不替用户删分支。

## 2. 待查（没有实现细节，不写结论）

- `trit-vcs` 的 ref 更新是否有 CAS/锁；并发 push 的行为。
- 分支删除/重命名后，哈希链事件日志如何记录。
- 分叉检测（两个提交共享祖先）是否已实现；`merge` 是否只有快进。
- 稀疏物化后，未物化目录在 status/diff 里如何表示。
- 分支保护/权限是否在中央仓侧存在。

## 3. 建议的验收面（将来补实现时）

- `ref update`：快进成功、分叉拒绝、并发 CAS 失败三类各一条测试。
- `pull --update-ref`：HEAD 与工作区一致；脏工作区零改动。
- 分支清理：squash 合并的分支能按 PR 状态识别并安全删除。
- worktree：同一分支不复用；会话分支命名唯一。
- 事件日志：分支删除/重命名后仍可验链与重放。
